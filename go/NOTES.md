# Notes: where the code goes beyond the contract

I wrote these notes while instrumenting `queueset.go` at `dbe731cf4b02`. Each item says what the contract cannot express, and the encoding I chose.

1. **Panics other than `slice bounds out of range`**: The contract's `panicked` is only the slice-bounds panic in `removeQueueAndUpdateIndexes`. On affected code, when `removeQueueIfEmptyLocked` wrongly removes a queue that held a *waiting* request, `qs.totRequestsWaiting` stays above the number of requests any queue in the slice holds. The next `dispatchAsMuchAsPossibleLocked` then reaches `findDispatchQueueToBoundLocked` with `minQueue == nil` and dies with `invalid memory address or nil pointer dereference` at `minQueue.requestsWaiting.Peek()`. This is a different panic with the same root cause, and it is far more common than the slice-bounds one (13 of 18 panicking seeds). Encoding: a `panic` record with the real message in `msg`, and `post.panicked = true`. A checker that wants `panicked` to mean only slice bounds should look at `msg`. The earlier removal event already breaks `safe_retirement` (a waiting request whose queue is not in the slice), so a checker loses nothing by treating every `panic` as terminal.
2. **Panic outside the timer callback**: The brief asks for recovery in the timer callback only. Panics also happen in `finishRequestLocked` (stale index on the immediate release path) and in dispatch (case 1) on the arrival, reconfigure, finish and timer paths. `finishRequestLocked` has the same recover-record-repanic wrapper as the timer. The patch does not instrument the other paths, because that would touch `StartRequest` and `setConfiguration`. Instead, the harness records them with a `recover` on the test goroutine, which takes `qs.lock`, writes the `panic` record, and re-panics. Such a record has no `req`, `queue`, `width` or `lingers`.
3. **A panic replaces the action's own record**: When `removeQueueIfEmptyLocked` panics in the timer, the instrumentation writes no `timer_fire` line, and the `panic` line carries the request's `req`, `queue`, `width` and `lingers`. Its `post` shows the partial effects: `releaseSeatsLocked` has already subtracted the seats, the request is no longer in `lingering`, and `panicked` is `true`. This matches the contract's `release` then `removeAt` order. In case 1 the `timer_fire` line comes first (the release finished) and the `panic` line follows.
4. **`desired` at top level**: The contract's text says only `reconfigure` carries `desired`, but its example also has it on `finish`. Every record carries it at top level, equal to `post.desired`.
5. **Ordering inside `post`**: `queues` is in slice order. `waiting` is in FIFO order. `executing` is in id order (the Go container is a set). `lingering` is in `req` order.
6. **Where records go relative to dispatch**: The instrumentation writes `arrive` before the dispatch loop that `StartRequest` runs next, `finish` before the loop that `finishRequestAndDispatchAsMuchAsPossible` runs next, `reconfigure` before the loop in `setConfiguration`, and `timer_fire` before the loop in the timer callback. Each `dispatch` is one line. So a dispatch always follows the action that made room for it.
7. **`init`**: The first `setConfiguration` writes it, if the harness has already installed `traceSink`. Per-`queueSet` counters number queues and requests from 0, and they number queues in creation order, so a reconfigure that grows the slice continues the numbering.
8. **Dispatch that loses the race with cancellation**: `dispatchLocked` has an early return when `decision.Set` fails (a cancelled request). This case is out of scope, and the instrumentation writes no record for it.
9. **`width`**: It is `MaxSeats()`. The harness uses `InitialSeats == FinalSeats`, so the two never differ.
10. **`lingers`**: It is `AdditionalLatency > 0`, exactly the test in `finishRequestLocked`.
11. **Simultaneous timers**: The fake clock runs all events due at one `SetTime` in separate goroutines, so two timers due together would fire in a nondeterministic order. The harness gives every lingering request a distinct nanosecond offset and advances the clock one event at a time, so the traces are deterministic (two runs gave identical files). The real system can fire timers concurrently. Each timer callback takes `qs.lock`, so the model's interleaving semantics still covers them, but the harness never produces a trace in which two timers were due at the same instant.
12. **The Go-side counters are only a classifier**: The harness computes `early_removals`, `wrong_removals` and `wrong_busy` in `logs/*/summary.txt` by comparing consecutive snapshots. They decide which seeds count as having hit the bug. The Lean checker is the authority on the traces.
