# Notes: where the code goes beyond the contract

Written while instrumenting `queueset.go` at `dbe731cf4b02`. Each item says what the contract cannot express, and the encoding I chose.

1. **Panics other than `slice bounds out of range`.** The contract's `panicked` is only the slice-bounds panic in `removeQueueAndUpdateIndexes`. On affected code a wrongly removed queue that held a *waiting* request leaves `qs.totRequestsWaiting` above the number of requests any queue in the slice holds. The next `dispatchAsMuchAsPossibleLocked` then reaches `findDispatchQueueToBoundLocked` with `minQueue == nil` and dies with `invalid memory address or nil pointer dereference` at `minQueue.requestsWaiting.Peek()`. This is a different panic with the same root cause, and it is far more common than the slice-bounds one (13 of 18 panicking seeds). Encoding: a `panic` record with the real message in `msg`, `post.panicked = true`. A checker that wants `panicked` to mean only slice bounds should look at `msg`. The earlier removal event already breaks `safe_retirement` (a waiting request whose queue is not in the slice), so nothing is lost by treating every `panic` as terminal.
2. **Panic outside the timer callback.** The brief asks for recovery in the timer callback only. Panics also happen in `finishRequestLocked` (stale index on the immediate release path) and in dispatch (case 1) on the arrival, reconfigure, finish and timer paths. `finishRequestLocked` has the same recover-record-repanic wrapper as the timer. The other paths are not instrumented in the patch (that would touch `StartRequest` and `setConfiguration`); the harness records them with a `recover` on the test goroutine, which takes `qs.lock`, writes the `panic` record, and re-panics. Such a record has no `req`, `queue`, `width`, `lingers`.
3. **A panic replaces the action's own record.** When `removeQueueIfEmptyLocked` panics in the timer, no `timer_fire` line is written; the `panic` line carries the request's `req`, `queue`, `width`, `lingers`. Its `post` shows the partial effects: seats already subtracted, request no longer in `lingering`, `panicked: true`. This matches the contract's `release` then `removeAt` order. In case 1 the `timer_fire` line comes first (release finished) and the `panic` line follows.
4. **`desired` at top level.** The contract's text says only `reconfigure` carries `desired`, its example also has it on `finish`. Every record carries it at top level, equal to `post.desired`.
5. **Ordering inside `post`.** `queues` is slice order. `waiting` is FIFO order. `executing` is sorted by id (the Go container is a set). `lingering` is sorted by `req`.
6. **Where records go relative to dispatch.** `arrive` is written before the dispatch loop that `StartRequest` runs next. `finish` is written before the loop that `finishRequestAndDispatchAsMuchAsPossible` runs next. `reconfigure` is written before the loop in `setConfiguration`. `timer_fire` is written before the loop in the timer callback. Each `dispatch` is one line. So a dispatch always follows the action that made room for it.
7. **`init`.** Written by the first `setConfiguration`, if `traceSink` is already installed. Ids: queues and requests are numbered from 0 by per-`queueSet` counters, queues in creation order, so a reconfigure that grows the slice continues the numbering.
8. **Dispatch that loses the race with cancellation.** `dispatchLocked` has an early return when `decision.Set` fails (a cancelled request). Out of scope, no record is written.
9. **`width`** is `MaxSeats()`. The harness uses `InitialSeats == FinalSeats`, so the two never differ.
10. **`lingers`** is `AdditionalLatency > 0`, exactly the test in `finishRequestLocked`.
11. **Simultaneous timers.** The fake clock runs all events due at one `SetTime` in separate goroutines, so two timers due together would fire in a nondeterministic order. The harness gives every lingering request a distinct nanosecond offset and advances the clock one event at a time, so traces are deterministic (checked: two runs give identical files). The real system can fire timers concurrently. Each takes `qs.lock`, so the model's interleaving semantics still covers them, but the harness never produces a trace in which two timers were due at the same instant.
12. **The Go-side counters are only a classifier.** `early_removals`, `wrong_removals` and `wrong_busy` in `logs/*/summary.txt` come from comparing consecutive snapshots in the harness. They decide which seeds are listed as having hit the bug. The Lean checker is the authority on the traces.
